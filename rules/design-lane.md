# Design lane — anti-slop, triggered by task type

Design skills activate when a task touches UI/UX surfaces — new screens, component work, visual polish, accessibility. Not always-on; not gated by a rigor dial. Trigger on task shape, same as any other skill.

*Drift canary applies to this file — see `WORKFLOW.md`'s "Drift canary" note.*

## Sequence

**Root cause of "still boring" findings, 2026-08-22:** the sequence below used to run `ui-ux-pro-max` (a *review-against-a-design-system* tool) first and never invoked `impeccable init`/`shape` — its own *plan-before-code* commands — until step 6+, by which point the generic version was already built. The tools to fix this were already installed; they just weren't sequenced to run before code got written. Steps 1–2 below are the fix — read this note before assuming a new dependency is the answer to a future "output is still generic" report.

1. **Pre-UI exploration + forced context, before any code.** For new screens/flows/information architecture, run `impeccable init` (or `shape` if a `PRODUCT.md`/`DESIGN.md` already exists) — it gathers brand-vs-product classification, audience, voice, and anti-references, and writes context every later command reads. Do not skip straight to `ui-ux-pro-max` or component search first; `impeccable`'s own docs frame this as the step everything else builds on. **When the user has real reference images** (screenshots, a moodboard, Pinterest-style captures), treat those as the primary input alongside brand context — show the vibe instead of describing it. Upload them with the brief.
2. **Forced aesthetic commitment — pick one extreme, name it, write it down.** Before writing a single CSS rule: state purpose, tone, constraints, and differentiation, then commit to *one* named direction (e.g. brutalist, editorial, retro-futuristic, luxury, maximalist) — not a blend, not "clean and modern." Default away from generic AI-slop fonts (Inter, Roboto, Arial, system-ui, Space Grotesk) unless the brief specifically calls for restraint. **Provenance, stated plainly:** this exact mechanism — 4-question framework + named-extreme commitment + font blocklist — used to ship as Anthropic's own official `frontend-design` Claude Code skill (`github.com/anthropics/skills`), but was removed in a 2026-06-09 rewrite (commit `2235be7`); the skill's *current* live version uses looser prose and no longer names a font blocklist or forces a named extreme. Multiple blog posts describe the mechanism as current when it isn't — verified directly against the live `SKILL.md`, not taken from those posts. Adopted here as native prose specifically *because* it's no longer safe to depend on the upstream skill for it. **When step 1 supplied reference images, the named direction is derived from what's actually in them** — describe the extreme already shown, don't pick one from the list above in the abstract. The list above is vocabulary for naming a shown direction, not a blind menu.
3. **Design intelligence** — `ui-ux-pro-max` for typography, spacing, color, accessibility, and anti-slop review against an established design system, now applied *against the committed direction from step 2*, not as the first and only design input. Already available as a Claude Code skill in this environment.

   **Optional ad hoc reference — The Component Gallery** (`component.gallery`, Iain Bean) — when unsure what a component type is even called or how real systems document it, it catalogs 60 components across 95 real-world design systems (Atlassian, GOV.UK, Shopify Polaris, etc.), 2,676 examples. Documentation/terminology reference only, no code output — not a manifest dependency, just a browse-when-stuck resource.
4. **Brand-specific reference** — when a task explicitly needs to mimic a *named* real product's look (e.g. "build this like Stripe/Linear"), pull the single matching file from `awesome-design-md`'s `design-md/` collection (see `skills/manifest.yaml`) for concrete color/typography/spacing tokens — don't bulk-vendor the repo, copy only the one company's `DESIGN.md` a task needs, and treat it as an "inspired interpretation" reference to spot-check against the live site, not an authoritative reverse-engineered spec.
5. **Component search** — shadcn MCP first, for existing component patterns before hand-rolling new ones. Two verified registry sources ride this same mechanism (add the namespace to `components.json`, install via `npx shadcn@latest add @<ns>/<name>` — see `skills/manifest.yaml`):
   - **KokonutUI** (`@kokonutui`) — general-purpose Tailwind/shadcn components.
   - **Bklit UI** (`@bklit`) — charts/data-visualization components; pairs with the bundled `dataviz` skill for chart-heavy work.

   **React Bits** (`reactbits.dev` / `github.com/DavidHDev/react-bits`) — pre-built animated/personality components; check here before hand-assembling motion from step 6's Motion/Anime.js primitives below. Does **not** ride the shadcn-registry mechanism above — a standalone npm/copy-paste install, confirm its own docs before wiring in. License permits building this org's own products with it, not reselling/redistributing the components themselves — see `skills/manifest.yaml`.
6. **Animation** — when a component needs motion, prefer **Motion** (React/JS, formerly Framer Motion) for component-level gestures/layout/springs, or **Anime.js** for lower-level DOM/SVG/canvas sequences. Both are libraries the agent imports and writes code against, not installable skills — see `skills/manifest.yaml`'s `watched_libraries` for why they aren't manifest entries. (Note: KokonutUI is itself built on Motion, so it may already be a transitive dependency once installed.)

   **Interaction-pattern transitions (modals, dropdowns, badges, page transitions)** — check **transitions.dev** first (`npx skills add Jakubantalik/transitions-dev`) before hand-building these from Motion/Anime.js primitives. Installable skill, 27+ production-ready snippets, `prefers-reduced-motion` baked into every one. See `skills/manifest.yaml`.
7. **Verification — render-before-judging, hard gate, plus a pass/fail rule gate.** Any polish/redesign task ends with an actual browser/Playwright screenshot at 1× DPR, viewed whole, compared against a "before." Never mark visual/polish work done from source review, DOM-state, or jsdom checks alone — those don't render pixels, so they can't catch e.g. a `box-shadow` in black on a near-black `#0a0e14` background rendering nothing. That's a technical fact, not a taste call, and only a screenshot catches it. Type-checking and test suites verify code correctness, not visual correctness — say so explicitly if browser verification isn't possible in a given environment. Alongside the screenshot, run `anti-slop`'s Delivery Gate (see `skills/manifest.yaml`) — a rule-tiered PASS/FAIL filter (38 rules, no prescribed style of its own) that catches slop patterns the screenshot alone won't name.

   **Mechanically checked, not just stated.** Same self-graded-prose problem as the drift canary and the review-gate — a commit that ships a touched UI file with no screenshot/Playwright evidence anywhere in the session gets logged, non-blocking, by `memory/hooks/design-lane-gate-check.js` (opt-in, same `--with-memory-hooks` flag). See `memory/SPEC.md`'s "Design-lane gate memory" section.

   **Screenshot tooling footgun:** `fullPage: true` combined with `position: sticky` elements produces stitching artifacts that look like broken layout but aren't. Verify a suspected layout bug with `getBoundingClientRect()` or a plain (non-fullPage) viewport screenshot before reporting it.

   **Pointing beats describing, when iterating on already-rendered UI:** prefer a tool like **Agentation** (click an element, get its exact selector/position, hand that to the agent) over prose ("the blue button in the sidebar") once something is on screen to point at. Noncompete license (PolyForm Shield) — fine for this org's own internal/product work, not for building something that competes with Agentation itself. See `skills/manifest.yaml`.

8. **Concept vs. execution — stop after two rejections.** If the same element gets rejected twice in a row, stop iterating its execution (materials, scale, lighting, spacing — whatever knob you're turning) and ask whether the concept itself is wrong. More discipline on a bad idea (better shaders, more zoom) doesn't save it — this is `impeccable`'s own polish-vs-redesign distinction, applied as a trigger condition rather than something to notice only after five rounds. A needle-on-dial gauge that reads as a generic car dashboard is a concept problem; no amount of material tuning fixes it.

9. **Open creative direction — don't default to restraint.** When the brief is genuinely "wow me" / open-ended, the conservative option is not automatically "(Recommended)." Framing an open creative ask as multiple-choice with a pre-loaded recommendation shapes the answer toward caution the user didn't ask for. For genuinely open creative direction: either build the bold option and show it, or ask neutrally without a labeled default. `impeccable bolder` ("amplify boring designs") is the concrete command for the case where output already reads as generic and needs correcting after the fact; `impeccable quieter` is its inverse when a build overshoots.

   **Concrete mechanism for open-ended briefs:** a single build, iterated on rejection, tends to regress toward the safe default — the exact failure this step warns against. When the user has *explicitly* opted into multi-agent orchestration (an "ultracode" request, or an explicit ask to use a workflow — the `Workflow` tool's own opt-in requirement; never invoke it unprompted for this), use its judge-panel pattern to generate several genuinely different directions in parallel (vary layout/structure, not just color, from the same brief/moodboard) and score them, rather than building one and asking "is this bold enough?" Without that opt-in, fall back to this step's existing guidance — ask neutrally, or build the bold option and show it.

## Benchmarked against an external methodology (2026-08-22)

Compared against Raha's "How to Design With AI" (YC Head of Design walkthrough, shared via Notion) — three pillars: name a component library instead of letting the agent invent one, show a real moodboard instead of describing a vibe, generate many variants and pick rather than iterating on one. Result: step 5's shadcn-first component search already matched pillar 1; pillars 2 and 3 were real gaps, now folded into steps 1, 2, and 9 above, plus a new library (React Bits, step 5) and a new pointing tool (Agentation, step 7) adopted into `skills/manifest.yaml`. A third named tool, `interior.dev`, could not be found under any spelling via search — no repo, no site, no press hit; not adopted, and not to be re-proposed without a direct working link (same disposition as the manifest's `unverified_excluded` list).

## Anti-patterns (default-reach mistakes, name them so they don't recur)

- **Full-bleed hairline section dividers** on data-heavy/report-style pages — a default a model reaches for without being told; don't add unless asked.
- **Box-shadow/border in a color close to the background** — invisible in practice, only caught by an actual screenshot (see render-before-judging above).
- **Skipping straight to `ui-ux-pro-max`/component search on a new screen without step 1–2's context + commitment first** — the specific sequencing mistake this file's 2026-08-22 pass was written to correct. Named so it doesn't quietly regress back.

## Evaluated and rejected

Two founder-submitted candidates turned out to be human-only, browser-based design tools with no API/MCP/CLI surface an agent could invoke — **Brik AI** (prompt-to-motion-graphics generator) and **Wevi.ai** (prompt-to-demo-video generator). Both produce visual/video assets, not code, and neither has a programmatic integration point. Kept in `skills/manifest.yaml`'s `reviewed_rejected` list with rationale so they aren't re-proposed without cause; see `skills/RESEARCH.md` §6 for the full research trail.

`heygen-com/hyperframes` (HTML→video rendering, 42k★) — audited 2026-08-22 for a Zarak-submitted adoption question, passes hygiene (CodeQL, `SECURITY.md`, 30 contributors, no install-lifecycle scripts, verified via `gh api` not secondhand fetch) but is genuinely out of scope here: it renders *video*, not UI, and doesn't touch the slop problem this file exists to solve. Not added to any trigger category — no video/motion-graphics task shape exists in this pack yet. Revisit if one does; see `skills/manifest.yaml`'s `reviewed_rejected` for the full disposition (not a safety rejection, an out-of-scope one).
